# S-1 — MRTR surface of `session.call_tool` (task F0-01)

> Status: done 2026-10-31 · Informs: DD-001, DD-004, Flow C (§3.3), REQ-HSH-040/041/043/045, REQ-INV-005

## Question

With `mcp>=2.3,<2.4`:

- (a) What is the exact signature of `client.session.call_tool(...)` for the MRTR path
  (`allow_input_required`, `input_responses`, `request_state`, progress callback), the
  shape of `InputRequiredResult`, and how `mcp.Client(...)` is constructed?
- (b) Can one elicitation round and one sampling round be driven by hand?
- (c) What does a registered callback returning `ErrorData` produce under modern (MRTR)
  vs legacy (server-initiated request)?
- (d) Do progress notifications reach the progress callback during `call_tool`?

## Answer

### (a) Signatures and types

`ClientSession.call_tool` (implementation signature, four `@overload`s narrow the return):

```python
async def call_tool(
    self,
    name: str,
    arguments: dict[str, Any] | None = None,
    read_timeout_seconds: float | None = None,
    progress_callback: ProgressFnT | None = None,      # positional-or-keyword, NOT keyword-only
    *,
    input_responses: types.InputResponses | None = None,
    request_state: str | None = None,
    meta: RequestParamsMeta | None = None,
    allow_input_required: bool = False,
    allow_claimed: bool = False,
) -> types.CallToolResult | types.InputRequiredResult | types.Result
```

- With `allow_input_required=True, allow_claimed=False` the overload returns
  `CallToolResult | InputRequiredResult`.
- `allow_input_required=False` + server returns input-required → `RuntimeError`
  ("Server returned InputRequiredResult; pass allow_input_required=True …").
- A non-error `CallToolResult` is **re-validated against the tool's output schema inside
  `session.call_tool`** (`validate_tool_result`); failure raises **`RuntimeError`**, not
  `MCPError`. If the tool was never listed, the session calls `list_tools()` first.
- A result claimed by a client extension with `allow_claimed=False` raises
  `UnexpectedClaimedResult`.
- `ProgressFnT`: `async def __call__(self, progress: float, total: float | None, message: str | None) -> None`.

`InputRequiredResult(Result)` (from `mcp_types`, re-exported as `mcp.types`): fields
`meta`, `result_type: Literal["input_required"]`, `input_requests: dict[str, InputRequest] | None`,
`request_state: str | None`; a validator requires at least one of the two.
`InputRequest = CreateMessageRequest | ListRootsRequest | ElicitRequest` (discriminated by
`.method`); `InputResponse = CreateMessageResult | CreateMessageResultWithTools | ListRootsResult | ElicitResult`
— **there is no error arm**.

`mcp.Client` is a dataclass: `Client(server, *, raise_exceptions=False, read_timeout_seconds=None,
sampling_callback=None, sampling_capabilities=None, list_roots_callback=None,
logging_callback=None, log_level=None, message_handler=None, client_info=None,
mode="auto", prior_discover=None, elicitation_callback=None, input_required_max_rounds=10,
extensions=None, cache=CacheConfig())`.
`server` is `Server | MCPServer | Transport | StdioServerParameters | str` (str = Streamable
HTTP URL). `mode` is `"auto" | "legacy" | "<modern version>"`. Extensions are
`ClientExtension` instances; `mcp.client.advertise(identifier, settings=None)` builds an
ad-only one. No client-side Apps extension class exists in 2.3.0 (only server side), so the
Host advertises `io.modelcontextprotocol/ui` with `advertise(...)`.

Callback protocols (`mcp.client.session`): `SamplingFnT(context: ClientRequestContext,
params: CreateMessageRequestParams) -> CreateMessageResult | CreateMessageResultWithTools | ErrorData`;
`ElicitationFnT(context, params: ElicitRequestParams) -> ElicitResult | ErrorData`;
`ListRootsFnT(context) -> ListRootsResult | ErrorData`; `LoggingFnT(params: LoggingMessageNotificationParams) -> None`;
`MessageHandlerFnT(message: ServerNotification | Exception) -> None`.
`ClientRequestContext(session, request_id, meta=None)` — on MRTR `request_id` is the
`input_requests` **key**; on legacy it is the server's JSON-RPC id.

```python
import inspect, mcp_types as types
from mcp import Client
from mcp.client.session import ClientSession
print(inspect.signature(ClientSession.call_tool))
print(inspect.signature(Client.__init__))
print(list(types.InputRequiredResult.model_fields))  # ['meta', 'result_type', 'input_requests', 'request_state']
```

### (b) Manual elicitation + sampling rounds

Works identically in-process and over stdio (negotiated `2026-07-28` via the `auto` probe):

```python
session = client.session
result = await session.call_tool("two_rounds", {}, progress_callback=on_progress, allow_input_required=True)
rounds = 0
while isinstance(result, types.InputRequiredResult):
    responses = {}
    for key, req in (result.input_requests or {}).items():
        if isinstance(req, types.ElicitRequest):
            responses[key] = types.ElicitResult(action="accept", content={"name": "Ada"})
        elif isinstance(req, types.CreateMessageRequest):
            responses[key] = types.CreateMessageResult(
                role="assistant", content=types.TextContent(type="text", text="Hello Ada!"), model="fake")
    rounds += 1
    result = await session.call_tool("two_rounds", {}, progress_callback=on_progress,
                                     input_responses=responses, request_state=result.request_state,
                                     allow_input_required=True)
# observed: round 0 {'ask': ElicitRequest}, state 'r1'; round 1 {'llm': CreateMessageRequest},
#           state 'r2:Ada'; final CallToolResult "Ada -> Hello Ada!" after rounds == 2
```

`request_state` came back byte-exact. `session.dispatch_input_request(ClientRequestContext(session=s,
request_id=key), req)` is a public method that routes one `InputRequest` through the
registered callbacks (the same table the legacy path uses); the Host may use it or call its
`InputRequestRouter` directly.

### (c) Callback returning `ErrorData`

**Modern, SDK auto-loop (`client.call_tool`)**: the driver raises
`MCPError.from_error_data(err)` locally — `MCPError(code=-32001, message="user refused (spike)")`
with `e.error` = the `ErrorData`. Sibling input requests of the same round are cancelled.
**Nothing is sent to the server**; the MRTR exchange is simply abandoned.

**Modern, manual loop**: `ErrorData` cannot be sent — putting it into `input_responses`
fails locally with `pydantic.ValidationError` (CallToolRequestParams). Refusal must be either
(i) abort the loop client-side (no retry), or (ii) answer with a protocol-level refusal value
(`ElicitResult(action="decline"|"cancel")`, which the server received as
`{"action": "decline"}`). Sampling has no decline arm.

**Legacy (`mcp` 1.30 server, stdio)**: the 2.3 client's `_on_request` converts the
`ErrorData` into a JSON-RPC error response to the server-initiated request. The server's
`ctx.elicit` / `create_message` raises `McpError(ErrorData(code, message))`; what the Host
then receives is **whatever the server tool decides**:

```
two_rounds (catches)        -> CallToolResult is_error=False "ELICIT_RAISED McpError: ErrorData(code=-32001, ...)"
two_rounds_unguarded        -> CallToolResult is_error=True  "Error executing tool two_rounds_unguarded: user refused (spike)"
sampling refused (catches)  -> CallToolResult is_error=False "SAMPLE_RAISED McpError: ErrorData(code=-1, ...)"
```

`session.call_tool(..., allow_input_required=True)` against a legacy server returns a plain
`CallToolResult` (never `InputRequiredResult`); the callbacks are invoked mid-call.

**Surprise — attribution**: a `ContextVar` set around `session.call_tool` **is not visible**
in callbacks on the legacy path (`inv=None` for every callback); legacy callbacks run in the
session's own task group (context of `Client.__aenter__`). In the modern auto-loop the
`ContextVar` *is* visible (`inv=inv-auto-ok`), because the driver dispatches from the caller's
task. On stdio there is also no wire-level link from a server-initiated request to the
originating `tools/call`, and `ClientRequestContext` carries none.

```python
# drive_legacy.py excerpt — callbacks log CURRENT_INVOCATION.get()
token = CURRENT_INVOCATION.set("inv-ok")
await client.session.call_tool("two_rounds", {}, allow_input_required=True)
# LOG: elicitation_cb inv=None request_id=0 / sampling_cb inv=None request_id=1
```

### (d) Progress

Yes, on both eras and both transports. `progress_callback(progress, total, message)` is
called for each `notifications/progress` of the request it was passed to. In MRTR each leg
is a new request (new JSON-RPC id / progress token), so the callback must be passed on
**every** leg; it was, and notifications arrived from all three legs:

```python
progress = []
async def on_progress(p: float, total: float | None, message: str | None) -> None:
    progress.append((p, total, message))
await client.session.call_tool("progress", {}, progress_callback=on_progress, allow_input_required=True)
# modern stdio: [(0.0, 1.0, 'leg state=None'), (1.0, 3.0, 'step 1'), (2.0, 3.0, 'step 2'), (3.0, 3.0, 'step 3')]
# legacy stdio: [(1.0, 3.0, 'step 1'), (2.0, 3.0, 'step 2'), (3.0, 3.0, 'step 3')]
```

### Other observations

- Auto-loop cap: `Client(input_required_max_rounds=N)` raises
  `mcp.InputRequiredRoundsExceededError` (`.max_rounds`) on the (N+1)-th `InputRequiredResult`;
  default 10. Equivalent to Flow C's "8 fulfilled rounds, error on the 9th input-required".
- The SDK driver handles **state-only** results (`request_state` without `input_requests`) by
  sleeping 50 ms doubling to 250 ms and retrying with `input_responses=None`. Flow C does not
  model this case.
- `Client.call_tool` adds two behaviours the manual loop loses: (1) on a modern connection a
  `HEADER_MISMATCH` (`-32020`) error triggers one re-list (`list_tools(cache_mode="refresh")`)
  and one resend; (2) extension result claims are resolved. (2) is irrelevant while the Host
  only uses `advertise(...)`; (1) must be replicated (relevant only on Streamable HTTP, where
  `Mcp-Param-*` headers are derived from the last `list_tools` entry).
- The legacy 1.30 server logs pydantic validation errors to stderr for the `server/discover`
  probe before falling back to `initialize`; harmless, but it will appear in the stderr ring
  buffer (S-2) of every legacy stdio Server connected with `mode="auto"`.

## Impact

**DD-001 confirmed** for the modern era: `client.session.call_tool(..., allow_input_required=True)`
exposes everything the own loop needs (per-round control, `request_state` passthrough,
per-leg progress), and the signature matches the plan except that `progress_callback` is
positional-or-keyword (4th parameter) rather than keyword-only — pass it by keyword.

Amendments required (**Delta Spec required**, proposed id `changes/2026-11-s1-mrtr-findings/`):

1. **Flow C / REQ-HSH-045 — legacy attribution.** The `ContextVar` mechanism does not work on
   legacy connections; as designed, *every* legacy input request would be attributed to
   `human:ui`, including those triggered by an agent Consumer (weaker consent scoping, Art. 3).
   Replace with a per-Server in-flight registry: if exactly one Host request (tool call or
   read) is in flight on that Server, correlate to it; otherwise `human:ui` (or serialize
   input-requiring requests per legacy Server — decision for the Delta Spec).
2. **Flow C — legacy sampling deny.** On legacy, denial reaches the Server as a JSON-RPC
   error and the Host gets back an arbitrary `CallToolResult` (`is_error` true or false). The
   Invoker must record the denial on the correlated invocation and override the outcome to
   `denied/sampling_denied`. Depends on (1).
3. **DD-004 — legacy timeout.** On legacy the human wait happens inside a single
   `session.call_tool` leg, so "per-leg `fail_after(remaining)`" counts human time. Proposed:
   hold the leg in a `CancelScope` and extend its `deadline` by the prompter-wait duration
   measured in the callback (needs (1); `CancelScope.deadline` mutation not yet exercised in
   this spike).
4. **Flow C — loop details.** (a) handle state-only `InputRequiredResult` (retry with
   `input_responses=None` and backoff; count it as a round toward the cap of 8);
   (b) on `MCPError.code == -32020` on a modern connection, re-list once and resend once;
   (c) classify `RuntimeError` from `session.call_tool` (output-schema mismatch, or an
   unexpected `InputRequiredResult`) as `protocol_error`; (d) a modern refusal of sampling is a
   client-side abort (no retry, nothing sent), a refused elicitation may be sent as
   `ElicitResult(action="decline"|"cancel")`; `ErrorData` is never placed in `input_responses`.
5. **Reads (REQ-HSH-046) via auto-loop** remain valid: `ContextVar` attribution works in the
   modern auto-loop; a callback `ErrorData` surfaces as `MCPError` with the callback's code, so
   the router must use distinguishable codes (e.g. one for `sampling_denied`) to map to
   `InputRequestError` codes. Legacy reads inherit issue (1).

## Contract assertions

Task F1-11 contract tests must pin (against `mcp` 2.3.x):

- `inspect.signature(ClientSession.call_tool)` parameters, in order: `self, name, arguments=None,
  read_timeout_seconds=None, progress_callback=None, *, input_responses=None, request_state=None,
  meta=None, allow_input_required=False, allow_claimed=False`.
- `session.call_tool(..., allow_input_required=True)` returns `InputRequiredResult` for an
  input-requiring modern tool; with the default `False` it raises `RuntimeError`.
- `InputRequiredResult` has `input_requests: dict[str, ElicitRequest | CreateMessageRequest | ListRootsRequest] | None`,
  `request_state: str | None`, `result_type == "input_required"`; constructing it with neither
  field raises `ValidationError`.
- `request_state` round-trips byte-exact through retry; each retry carries new
  `input_responses` keyed by the server's keys.
- `InputResponses` rejects `ErrorData` values (`pydantic.ValidationError` on
  `CallToolRequestParams`).
- `ProgressFnT` is called as `(progress: float, total: float | None, message: str | None)`
  for notifications of every leg it is passed to, on in-process and stdio transports, modern
  and legacy.
- Non-error `CallToolResult` with structured content violating the output schema →
  `RuntimeError` from `session.call_tool`.
- `Client` accepts keyword-only `sampling_callback`, `elicitation_callback`,
  `list_roots_callback`, `logging_callback`, `log_level`, `message_handler`, `mode`,
  `prior_discover`, `input_required_max_rounds`, `extensions`, `cache`, `read_timeout_seconds`;
  `mcp.client.advertise(identifier, settings)` returns a `ClientExtension`.
- Auto-loop: callback `ErrorData(code=c)` → `MCPError` with `.code == c` and `.error` the
  `ErrorData`; exceeding `input_required_max_rounds` → `InputRequiredRoundsExceededError`
  with `.max_rounds`.
- `ClientSession.dispatch_input_request(ctx, request)` exists and returns the callback's
  `InputResponse | ErrorData`.
- Legacy era: `session.call_tool(..., allow_input_required=True)` returns `CallToolResult`;
  callback `ErrorData` is delivered to the Server as a JSON-RPC error with the same code and
  message; a `ContextVar` set by the caller is **not** visible inside the callback (pin this so
  an SDK change that starts propagating context is noticed).
- `ClientRequestContext.request_id` equals the `input_requests` key on MRTR dispatch.
- `HEADER_MISMATCH == -32020` (`mcp_types.jsonrpc`).
