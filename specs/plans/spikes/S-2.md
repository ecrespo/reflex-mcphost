# S-2 — stdio stderr capture and exit detection (task F0-02)

> Status: done 2026-10-31 · Informs: DD-002, Flow B (§3.3) step 8, REQ-CON-005/007/008/009, REQ-NFR-030
> Spike code: `spikes/S-2/` (throwaway, not merged)

## Question

With `mcp>=2.3,<2.4`:

1. What types does `mcp.client.stdio.stdio_client(params, errlog=...)` accept for stderr
   capture: file object, text stream, anything with `write`, a file descriptor, a callback?
2. Can a child Server's stderr be fed line by line into an in-memory ring buffer
   (`collections.deque(maxlen=N)`) without a dedicated OS thread, under anyio? Windows caveats?
3. A supervisor parked inside `async with mcp.Client(<stdio transport>) as client:` — how does
   it learn the child exited (SIGKILL, or exit on its own)? Exception in the body, a
   `message_handler` call, or polling? Latency over ~10 trials (target < 1 s).
4. How does the SDK shut down the stdio child on context exit, compared with REQ-CON-008
   (close stdin, wait up to 5 s, terminate, kill after a further 5 s)?

## Answer

### 1. Accepted `errlog` types

Signature (2.3.0): `stdio_client(server: StdioServerParameters, errlog: TextIO = sys.stderr)`.
`errlog` is passed **unchanged** as `stderr=` to `anyio.open_process` (POSIX, `start_new_session=True`)
or, on Windows, to `anyio.open_process` / the `subprocess.Popen` fallback. So the real contract is
`subprocess`'s: **anything with a working `fileno()`, an int fd, `subprocess.DEVNULL`/`PIPE`, or
`None`**. The `TextIO` annotation is narrower than what runs, and nothing in the SDK ever calls
`errlog.write`.

| `errlog` value | Result | Notes |
|---|---|---|
| `open(path, "w")` text file | OK, captured | satisfies the `TextIO` annotation |
| `open(path, "wb")` binary file | OK, captured | needs `# type: ignore[arg-type]` under mypy strict |
| raw `int` fd | OK, captured | same typing caveat |
| `sys.stderr` (default) | OK | the child writes straight to the Host's stderr |
| `subprocess.DEVNULL` | OK | discards |
| `subprocess.PIPE` | session works, **unusable** | the SDK never reads it and the process object is not exposed: the child blocks once the ~64 KiB pipe fills |
| `None` | OK | inherit |
| `io.StringIO()` | **FAIL** `UnsupportedOperation: fileno` | raised at spawn, before any process exists (no leak) |
| object with only `write()`/`flush()` | **FAIL** `AttributeError: ... 'fileno'` | same |
| callback | **FAIL** `AttributeError: ... 'fileno'` | same |

Also important: `Client(StdioServerParameters(...))` builds `stdio_client(srv)` with the default
`errlog=sys.stderr` and offers no way to pass `errlog`. To capture stderr the Host must build the
transport itself and pass it: `Client(stdio_client(params, errlog=...))` (any `mcp.client.Transport`
is accepted).

### 2. Ring buffer without a dedicated thread

Yes on POSIX: use a pipe whose read end is drained by an anyio task. The core of `spikes/S-2/s2lib.py`:

```python
class StderrRing:
    def __init__(self, maxlen=1000, encoding="utf-8"):
        self.lines = collections.deque(maxlen=maxlen)
        self.eof = anyio.Event()
        self._r, self._w = os.pipe()            # PEP 446: non-inheritable; subprocess dup2()s _w onto fd 2
        os.set_blocking(self._r, False)
        self._wfile = os.fdopen(self._w, "w")   # a real TextIO for the annotation

    def child_end(self): return self._wfile
    def close_parent_write_end(self): self._wfile.close()   # after spawn, else EOF never comes

    async def pump(self):
        buf = b""
        try:
            while True:
                await anyio.wait_readable(self._r)
                try:
                    chunk = os.read(self._r, 65536)
                except BlockingIOError:
                    continue
                if not chunk:
                    break                         # every writer gone (child + descendants)
                buf += chunk
                *complete, buf = buf.split(b"\n")
                for raw in complete:
                    self.lines.append((time.monotonic(), raw.decode(self._encoding, "replace")))
        finally:
            self.eof.set(); os.close(self._r)

ring = StderrRing(maxlen=50)
async with anyio.create_task_group() as tg:
    tg.start_soon(ring.pump)
    async with Client(stdio_client(params, errlog=ring.child_end())) as client:
        ring.close_parent_write_end()
        ...
```

Observed (`q2_ring_buffer.py`, fixture writing every 10 ms for 1.5 s): the deque held exactly the
last 50 lines, including `fixture: stdin EOF, run() returned` written during SDK shutdown, then
`ring.eof` fired. Threads: before `['MainThread']`; during `['MainThread', 'asyncio-waitpid-0']`
on asyncio and `['MainThread', 'Trio thread 0']` on trio. Both extra threads are the event loop's
child-process watcher and appear identically with `errlog=subprocess.DEVNULL` and no ring at all;
the stderr capture itself adds none.

Caveats:

- **Close the parent's copy of the write end right after the spawn.** Otherwise the reader never
  sees EOF. Better than the snippet above: close it inside the Host's own `Transport` wrapper right
  after `stdio_client.__aenter__` returns (spawn done, before the handshake), so a handshake that
  fails or is cancelled cannot leak it. Use a new pipe for each connection attempt.
- Backpressure: if the Host loop stalls, the child blocks on `write(2)` once the pipe is full
  (~64 KiB on Linux). Never stop draining while the child lives. Cap unterminated lines (the
  spike truncates at 64 KiB).
- Decode with `errors="replace"`: stderr is untrusted bytes (Art. 5), and Host logging must apply
  redaction to it before persisting anything.
- **Windows (from source, untested):** `anyio.wait_readable` supports only `SOCKET` handles on
  Windows ("File descriptors aren't supported", anyio 4.15 docstring), and an `os.pipe()` is an
  anonymous, non-overlapped pipe that the Proactor loop cannot read asynchronously. The thread-free
  approach therefore **does not carry over to Windows**. Allowed fallback (Art. 8, blocking behind
  `anyio.to_thread`): a loop of `await anyio.to_thread.run_sync(os.read, r, 65536, limiter=<dedicated
  CapacityLimiter>, abandon_on_cancel=True)`. This occupies one worker thread per live Server while
  blocked, so it must **not** use the default 40-token limiter. A per-OS strategy in
  `core.connection.transports` plus Windows CI (REQ-NFR-030) must confirm this. (An overlapped pipe
  from `asyncio.windows_utils.pipe` would avoid the thread but is asyncio-only and was not tried.)

### 3. Exit detection while parked inside `async with Client`

**The SDK does not tell the body.** In Part A (asyncio and trio, `auto` and `legacy`), after SIGKILL
or self-exit the body stayed parked for the whole 3 s window: no exception, no cancellation, and
`message_handler` was **never called**. The source explains this: `stdio_client.stdout_reader` closes
the read stream on EOF; `JSONRPCDispatcher.run` treats that as EOF (`_closed = True`,
`_fan_out_closed()` wakes pending requests with `MCPError(CONNECTION_CLOSED = -32000)`) and returns
quietly. `message_handler` only receives `Exception` *items* that the transport yields (such as
stdout parse errors), never end-of-stream. A request issued after the death fails at once (`ping` →
`MCPError -32000 'Connection closed'` in ~0.2 ms), but `ping` is removed in `2026-07-28` (SDK
warns: "only works under mode='legacy'"), so polling with requests is neither needed nor clean.

**Working approach: an EOF-observing `Transport` wrapper plus wait-any.** It uses only the public
`mcp.client.Transport` protocol and needs no polling:

```python
@asynccontextmanager
async def watched_stdio(params, errlog, watch: TransportWatch):
    async with stdio_client(params, errlog=errlog) as (read, write):
        yield _EofWatchingReadStream(read, watch), write   # proxy: receive() sets watch.closed on
                                                           # EndOfStream/ClosedResourceError/BrokenResourceError
async with Client(watched_stdio(params, ring.child_end(), watch), mode=mode) as client:
    async with anyio.create_task_group() as park:          # Flow B step 8
        park.start_soon(_wait_then_cancel, stop_requested, park.cancel_scope)
        park.start_soon(_wait_then_cancel, watch.closed, park.cancel_scope)
    # here: watch.closed.is_set() → reconnecting; else stop requested → disconnected
```

(The proxy forwards `__aiter__`/`__anext__`/`__aenter__`/`__aexit__`/`aclose` and, through
`__getattr__`, `last_context`, all of which `JSONRPCDispatcher.run` uses.)

Latency from kill to the supervisor waking (asyncio, Python 3.13, `mode="auto"`, 10 trials each, ms):

| Scenario | Transport EOF (min / median / p90 / max) | stderr-pipe EOF (median) | `Client.__aexit__` afterwards (median / max) |
|---|---|---|---|
| SIGKILL from the Host | 4.9 / 5.2 / 5.6 / 6.0 | 4.8 | 0.2 / 10.7 |
| Exit on its own (`os._exit(0)`) | 5.2 / 5.4 / 6.4 / 7.3 | 4.8 | 0.2 / 0.3 |
| Crash during an in-flight `call_tool` | 4.0 / 5.8 / 6.8 / 7.2 | 5.3 | 0.2 / 10.5 |

- In-flight request on crash: `call_tool` raised `MCPError` code `-32000` after 3.7–6.9 ms (this
  maps to `connection_lost` in Flow C step 7).
- trio (5 trials): median 5.6–6.6 ms. `mode="legacy"` (5 trials): median 5.3–5.8 ms. Python 3.11.15
  (3 trials): median 5.2–5.6 ms. **All well under the 1 s target.**
- Modern `client.listen()` (`q3b_listen.py`, 10 SIGKILL trials): the loop raised
  `mcp.client.subscriptions.SubscriptionLost` after a median of 5.2 ms. It is fast, but it **cannot
  be the stdio liveness signal**: it does not exist on legacy Servers or when no list-change filter
  applies, and Flow B row B.8 needs "listen lost, transport alive" (re-listen, stay `ready`) to be
  told apart from "transport dead". The supervisor checks `watch.closed` to classify a `SubscriptionLost`.
- The stderr-pipe EOF fires ~0.5 ms earlier, but it is only a hint: a Server may close or redirect
  its stderr, and descendants holding it keep it open. Transport EOF is authoritative because it is
  exactly the moment the session becomes unusable.
- Caveat (both signals): EOF means "every holder of the pipe is gone", not literally "the leader pid
  exited". A wrapper (`sh -c`, `npx`) whose grandchild keeps stdout open keeps the transport alive,
  which matches the session still working. A Server that closes stdout but keeps running looks
  dead, which is also correct for us. The SDK keeps the process object private (a local inside the
  `stdio_client` generator), so `returncode` is not available without reaching into internals.

### 4. SDK shutdown on context exit vs REQ-CON-008

Sequence (`stdio_client` `finally` → `shutdown()` → `_stop_server_process`), run inside
`anyio.CancelScope(shield=True)`:

1. close the session read stream; close the write stream; wait up to `_WRITER_FLUSH_TIMEOUT = 0.5` s
   for the writer to flush;
2. close the child's **stdin**; poll `returncode` every 10 ms for up to `PROCESS_TERMINATION_TIMEOUT = 2.0` s;
3. POSIX: `os.killpg(pgid, SIGTERM)` to the **whole process group** (the child is spawned with
   `start_new_session=True`), wait up to `FORCE_KILL_TIMEOUT = 2.0` s, then `killpg(SIGKILL)`.
   Windows: immediate **Job Object termination** (a hard kill; there is no graceful-terminate step);
4. wait up to `_KILL_REAP_TIMEOUT = 2.0` s for the death to be observed (otherwise log a warning and
   abandon); close the job (Windows) and stdout; close the asyncio subprocess transport.

Measured exit duration (`q4_shutdown.py`):

| Server behavior | SDK defaults | Constants patched to 5.0 / 5.0 | REQ-CON-008 expects |
|---|---|---|---|
| exits on stdin EOF | 0.11 s | 0.14 s | ≤ 5 s |
| ignores EOF, honors SIGTERM | 2.02 s (child logged SIGTERM) | 5.01 s | ~5 s, then terminate |
| ignores EOF and SIGTERM | 4.02 s (SIGKILL) | 10.01 s | ~10 s, then kill |
| same, caller **cancelled** inside the block | 4.01 s, `cancelled_caught=True` | — | — |

In every case the child was dead afterwards (`os.kill(pid, 0)` → `ProcessLookupError`).

Comparison: the **order** matches REQ-CON-008 (close stdin → wait → terminate → kill), and the SDK is
stronger on "no orphaned process" because it signals the whole process group or job. The
**timeouts differ** (2 s / 2 s instead of 5 s / 5 s). `PROCESS_TERMINATION_TIMEOUT` and
`FORCE_KILL_TIMEOUT` are module globals read at call time, so setting them takes effect
immediately (verified). They are process-wide, though, not per `Client`, and not documented API.
Shutdown is shielded: caller cancellation and `anyio.fail_after` cannot shorten it. Worst case for
one Client: 0.5 + 2 + 2 + 2 = 6.5 s with the defaults, or 0.5 + 5 + 5 + 2 = 12.5 s with the
REQ-CON-008 values. REQ-CON-009 (15 s total) is therefore only reachable if all Clients are
disconnected **concurrently** (each supervisor exits its own block in parallel), never one after
another. On Windows, "terminate, then kill after a further 5 s" collapses into one hard kill
after the stdin grace period.

## Impact

**DD-002 confirmed.** A supervisor task that owns and parks inside `async with Client(...)` works.
The body is not woken by the SDK, so the supervisor must park on *wait-any(stop, transport_closed)*
using an EOF-observing `Transport` wrapper (public `mcp.client.Transport` protocol, no polling,
~5 ms detection).

**Delta Spec required** (small, wording and mechanism only; no requirement is weakened). It should
cover:

- **Tech Design Flow B step 8:** replace "transport exception via message_handler … stdio process
  exit" with "transport read-stream EOF observed by the Host's `Transport` wrapper (stdio and
  HTTP); `SubscriptionLost` is classified by checking that signal". `message_handler` does not
  report EOF.
- **Tech Design §3.2 "Transport factory":** stdio must be built as `Client(<own Transport>)`, never
  `Client(StdioServerParameters)`, because the latter cannot capture stderr. The factory owns the
  per-attempt pipe, closes the parent write end after spawn, and uses a per-OS stderr reader:
  POSIX `wait_readable`, Windows `to_thread` with a dedicated limiter. Windows must be verified in CI.
- **REQ-CON-008 handling:** recommended option: keep the REQ and set
  `mcp.client.stdio.PROCESS_TERMINATION_TIMEOUT = FORCE_KILL_TIMEOUT = 5.0` once at Host start,
  documented as process-wide and pinned by a contract test. Alternative: amend REQ-CON-008 to the
  SDK's 2 s / 2 s policy. In both cases, add the Windows note (terminate = immediate Job Object
  kill) and state that REQ-CON-009 requires concurrent disconnects.

REQ-CON-005 (stdio process exit → `reconnecting`) and REQ-CON-007 (stderr into the Server's log
stream) are achievable as specified.

## Contract assertions

For `tests/contract/test_mcp_sdk_surface.py` (F1-11):

1. `inspect.signature(mcp.client.stdio.stdio_client)` has exactly the parameters
   `(server: StdioServerParameters, errlog: TextIO = sys.stderr)`, and it is an async context
   manager yielding a 2-tuple `(read_stream, write_stream)`.
2. `stdio_client(params, errlog=<os.fdopen(pipe_w, "w")>)`: stderr lines written by the
   `modern_stdio` fixture arrive on the pipe read end. Also, `errlog=io.StringIO()` raises
   `io.UnsupportedOperation` at spawn and no child process is left behind.
3. `mcp.Client` accepts an `mcp.client.Transport` (an async CM yielding `(read, write)`) as its first
   positional argument, and the dispatcher consumes the read stream via `async with` + `async for`
   (so the EOF-watching proxy works). Pinned live: after a SIGKILL of the fixture, the wrapper's
   `closed` event fires within 1 s.
4. After the child dies, the body of `async with Client` is **not** cancelled and `message_handler`
   is **not** called (if this changes, the supervisor could simplify; the test documents it). A
   pending request then raises `MCPError` with `error.code == mcp_types.CONNECTION_CLOSED` (`-32000`).
5. A modern `client.listen(tools_list_changed=True)` raises `mcp.client.subscriptions.SubscriptionLost`
   when the stdio child is killed.
6. `mcp.client.stdio` exposes module attributes `PROCESS_TERMINATION_TIMEOUT` and `FORCE_KILL_TIMEOUT`
   (floats; 2.0 by default in 2.3.0), and setting them changes the escalation timing (a Server that
   ignores EOF takes ≥ the patched value to exit). Only needed if the REQ-CON-008 option "patch
   constants" is chosen.
7. On exit from the `Client` block the child is dead even when the Server ignores stdin EOF and
   SIGTERM (POSIX), and the exit completes even if the enclosing scope was cancelled (shielded shutdown).
8. `Client(StdioServerParameters(...))` has no `errlog` path. Guard this by an import-linter or grep
   rule that `core` never constructs `Client(StdioServerParameters…)`, rather than by an SDK test.
