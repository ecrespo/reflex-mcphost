# S-3 — MCP Apps origin pair across browsers (task F0-03)

> Status: done 2026-10-31 (Safari proxied by Playwright WebKit; real Safari not verified)
> Informs: DD-012, DD-017, Flow F (§3.3), API §7, REQ-APP-002/003/011
> Spike code: `spikes/S-3/` (throwaway, not merged) · raw results: `spikes/S-3/results.json`

## Question

Does the DD-012 origin pair — Host UI on `http://127.0.0.1:<p1>`, sandbox proxy on
`http://localhost:<p2>` (`sandbox="allow-scripts allow-same-origin"`, empty `allow`), View
in an inner `srcdoc` iframe with a CSP `<meta>` and `sandbox="allow-scripts"` — work and
isolate in Chromium, Firefox and Safari?

1. Does a real MCP App (ext-apps, `2026-01-26` era) render, complete the
   `ui/initialize` → `ui/notifications/initialized` → `tool-input` → `tool-result`
   handshake, and get a View-initiated `tools/call` relayed proxy → UI → backend stub?
2. Are the UI origin's `document.cookie` and `localStorage` unreachable from the proxy and
   from the View? Can the View touch `parent.document`?
3. Does the UI accept messages only from the proxy window it created (`event.source ===
   proxyWindow`), rejecting forged messages from other windows?
4. A-03: if the UI is opened as `http://localhost:<p1>`, does it share cookies with the
   proxy origin (justifying the DD-017 `127.0.0.1`-only guard)?
5. IPv6: does `localhost` resolve and the proxy load when the proxy listens on `::1`?

## What was tried

- **Listeners** (`servers.py`, one process, separate sockets): UI `127.0.0.1:18741` (IPv4
  only, as DD-017 binds it); proxy `18742` bound to **both** `127.0.0.1` and `::1`
  (`IPV6_V6ONLY` socket for the v6 one); probe listeners `18743` (`::1` only) and `18744`
  (`127.0.0.1` only). Every proxy request is logged with `Host`, `Cookie` and client IP.
  The UI server also exposes `/api/app-html` (stands in for `resources/read`) and
  `POST /api/tools-call` (stub for `Invoker.call`, returns `STUB-<n>-<time>`).
- **UI** (`ui.html`): sets `ui_js=SECRET_JS` (JS cookie), receives `ui_http=SECRET_HTTP`
  (`HttpOnly`, `SameSite=Lax`) from the server, `localStorage.ui_secret=SECRET_LS`; creates
  the proxy iframe (`sandbox="allow-scripts allow-same-origin"`, `allow=""`), captures
  `proxyWindow = iframe.contentWindow` at creation, and accepts a message only if
  `event.source === proxyWindow && event.origin === PROXY_ORIGIN`. On `sandbox-proxy-ready`
  it sends `sandbox-resource-ready {html, csp: {}, sandbox: "allow-scripts"}`; answers
  `ui/initialize` (`protocolVersion "2026-01-26"`, `hostCapabilities {serverTools, logging}`,
  `hostContext` inline/light/en-US/UTC); after `initialized` sends `tool-input` then
  `tool-result`; relays `tools/call` to the stub; `-32601` for anything else with an id.
- **Proxy** (`proxy.html`, no CSP header): accepts parent messages only from
  `event.source === window.parent && event.origin === HOST_ORIGIN`; builds the CSP `<meta>`
  (restrictive default: `default-src 'none'; script-src 'unsafe-inline'; style-src
  'unsafe-inline'; img-src data: blob:; font-src data:; media-src data: blob:; connect-src
  'none'; frame-src 'none'; base-uri 'self'; object-src 'none'`), inserts it right after
  `<head>`, sets `inner.srcdoc`; forwards non-`ui/notifications/sandbox-*` messages to the
  View and View messages (identity check `event.source === inner.contentWindow`) to the
  parent with target origin `HOST_ORIGIN`. It also posts a self-probe (spike-only method
  `ui/notifications/sandbox-s3-probe`).
- **View probe** (spike instrumentation, injected by the UI at the top of `<head>`, before
  the App's module script): reads `self.origin`, `document.cookie`, `localStorage`,
  `parent.document`, `top.document`, `top.localStorage`; tries
  `fetch(<UI origin>/api/stats)`; posts a forged `tools/call` **directly to `top`**
  (bypassing the proxy); reports via `notifications/message` (logger `s3-probe`).
- **Forgers** (`forger.html`, served from the *proxy's* origin, so an origin-only check
  would pass): (a) a sibling iframe in the UI posting to `parent`; (b) a popup opened by a
  click posting to `window.opener`. Each sends a forged `tools/call` and a forged
  `sandbox-proxy-ready`.
- **Scenarios per engine** (fresh browser context each, `run.py`): `main` (UI on
  `127.0.0.1`, dual-stack proxy, click "Get Server Time", open popup); `a03` (UI opened as
  `http://localhost:18741`); `v6only` (proxy on `::1` only); `v4only` (proxy on
  `127.0.0.1` only); `navexfil` (extra, see below: the View navigates its own frame to

Notes on the observations:

- **The App needs no `'unsafe-eval'`.** Chromium and Firefox log two `script-src eval`
  CSP violations from the bundle (zod's JIT capability probe); the App works regardless.
  WebKit logged none. F7-06 must not treat these as failures.
- **Proxy page CSP is inherited by the `srcdoc` View.** The proxy was served without a CSP
  header on purpose: a stricter header (e.g. `script-src 'self'`) would also bind the
  View and break inline App bundles. Not exercised as a failure case; this follows from
  CSP policy-container inheritance for `srcdoc` documents.
- **The inner frame has origin `"null"`**, so the proxy can only check View messages by
  window identity (`event.source === inner.contentWindow`) and must post to the View with
  target `"*"`. The reference `basic-host` sandbox avoids this by giving the inner frame
  `allow-same-origin` and using `document.write` — that makes the View same-origin with
  the proxy, which DD-012 deliberately does not do.
- **Navigation is an exfiltration channel CSP does not close.** `sandbox="allow-scripts"`
  still lets the View navigate its own frame; `connect-src`/`frame-src` do not cover it,
  and there is no CSP `navigate-to`. Anything the Host sent to the View (tool input/result)
  can leave the machine that way. This is inherent to the spec's design (the reference
  host is equally exposed) and not an isolation failure of the UI origin, but it is a
  residual risk the Security section should state.
- **Engines resolve `localhost` themselves.** Python `getaddrinfo(AF_UNSPEC)` returned
  only `127.0.0.1`, but Chromium and WebKit connected over `::1`, and every engine reached
  a `::1`-only listener. A Python-side resolution check does not predict which family the
  browser will use; binding both stacks (DD-012) is what makes it work.
- Firefox requested `/favicon.ico` from the proxy origin (cookie-less); harmless.
- The A-03 UI page loaded because the browsers fell back to `127.0.0.1` for `localhost`
  (the UI server logged client `127.0.0.1`). In the real app, the DD-017 middleware would
  reject the backend `Host: localhost:<port>`, but the static frontend still loads and can
  set cookies on host `localhost`, which the proxy origin then shares.

## Impact

- **DD-012 confirmed** for Chromium, Firefox and WebKit (WPE): the `127.0.0.1` UI /
  `localhost` proxy pair renders the App, relays `tools/call`, and isolates cookies,
  `localStorage` and the DOM of the UI origin; the `event.source === proxyWindow` filter
  rejects every forged message tried.
- **DD-017 confirmed (A-03):** when the UI is opened as `localhost`, every engine sends
  the UI's cookies (including `HttpOnly`) to the proxy origin and exposes non-`HttpOnly`
  ones to proxy script. The `127.0.0.1`-only guard and the "open http://127.0.0.1:<port>"
  notice are justified.
- **Delta Spec recommended (small, no design change)** to pin what the spike showed into
  DD-012 / API §7 / §6.1:
  1. The proxy page must be served **without a CSP stricter than `build_csp`'s output**
     (the `srcdoc` View inherits it); the policy reaches the View only through the
     `<meta>`.
  2. Proxy ↔ View messaging: identity check `event.source === inner.contentWindow` and
     `postMessage(msg, "*")` toward the View (opaque origin); target origin =
     the pinned Host origin toward the parent. Proxy ↔ parent: `event.source ===
     window.parent && event.origin === <pinned Host origin>`.
  3. The default CSP must not include `'unsafe-eval'`; the sample App works without it.
  4. §6.1 must list View self-navigation as a known exfiltration path not mitigated by CSP.
     Optional mitigation to decide on: the proxy treats a second `load` event of the inner
     frame as a navigation and reports it so the Host tears the View down (limits damage
     but does not stop the first request).
  5. The DD-012 consequence "the CLI refuses to start if `localhost` does not resolve to
     loopback" should check **both** `AF_INET` and `AF_INET6` results (all returned
     addresses must be loopback); `AF_UNSPEC` alone hid `::1` on this host.
- **Real Safari remains unverified.** Playwright's WebKit is the WPE port (libsoup network
  stack, no ITP); Apple Safari uses CFNetwork and ITP, which could differ on cookie
  handling for `localhost`/`127.0.0.1` and on IPv6 loopback. Run F7-06 (or a manual pass of
  `spikes/S-3/run.py` scenarios) on macOS before release. **Update 2026-11-01:** that
  manual pass (F8-15) was waived by owner decision — no macOS / Safari available; Playwright
  WebKit (WPE) in the CI E2E on three engines is the `0.1.0` coverage and real Safari is a
  known limitation (Plan R-8 accepted; delta `changes/_archive/2026-11-safari-s4-decisions`).

## Contract assertions (for F7-06 E2E, all three Playwright engines)

Per engine, fresh context, UI at `http://127.0.0.1:<frontend_port>`, a fixture Server
exposing the vendored `basic-server-vanillajs` App:

1. Proxy iframe attributes: `sandbox == "allow-scripts allow-same-origin"`, `allow == ""`,
   `src` origin `http://localhost:<proxy_port>`; inner frame `sandbox == "allow-scripts"`,
   uses `srcdoc`, first child of `<head>` is the CSP `<meta>`, and that CSP contains
   `object-src 'none'`, `frame-src 'none'` (no `frameDomains`) and no `'unsafe-eval'`.
2. The View renders and shows the `tool-result` value delivered after `initialized`; the
   relay sent zero messages to the View before `ui/notifications/initialized`;
   `tool-input` precedes `tool-result`, each exactly once.
3. Clicking the App's button produces exactly one `Invoker.call` with
   `consumer = Consumer.app(server_id)` and one audit record; the View shows the result.
4. Inside the View (via `frame.evaluate`): `self.origin === "null"`; `localStorage` throws;
   `document.cookie` throws **or** returns `""` (WebKit returns `""`) — assert "does not
   contain the UI cookie", not "throws"; `parent.document` and `top.document` throw.
5. Inside the proxy frame: `document.cookie` contains no UI cookie and
   `localStorage` has no UI keys; the proxy request reached the server without UI cookies.
6. Forgeries are dropped and never reach the Invoker: a same-origin-as-proxy sibling iframe,
   a popup via `window.opener`, and the View posting straight to `top` each send
   `tools/call` → Invoker call count unchanged; a forged `sandbox-proxy-ready` does not
   trigger a second `sandbox-resource-ready`.
7. A-03 / DD-017: opening `http://localhost:<frontend_port>` shows the static
   "open http://127.0.0.1:<port>" notice, gets no backend websocket (403 on `Host`), and no
   App is rendered. (The cookie sharing itself is browser behavior already established
   here; the test asserts the guard, not the leak.)
8. IPv6: with the proxy listener on `127.0.0.1` and `::1`, the App renders in all engines;
   an additional run with only `::1` bound must still render (proves the `::1` listener is
   reachable, since Firefox prefers `127.0.0.1`).
9. CSP-violation console messages for `script-src eval` are tolerated; any other console
   error from the View fails the test.
