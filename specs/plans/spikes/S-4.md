# S-4 — CIMD with loopback redirect against a real authorization server (task F0-04)

> Status: closed 2026-11-01 with **plan B** (owner decision: no real CIMD-capable
> authorization server available; CIMD interop against a real AS not verified) ·
> Informs: DD-009, REQ-AUTH-002/003/010/011/012, Plan R-9
> Spike code: none — no real AS was reachable; the evidence is the in-repo fixture AS
> (`tests/fixtures/servers/auth_server.py`, F4-09a) and the tests that drive it.
> Delta: `changes/_archive/2026-11-safari-s4-decisions`

## Question

1. Does at least one real authorization server that advertises
   `client_id_metadata_document_supported` accept the project's Client ID Metadata Document
   (`https://blog.seraph.to/reflex-mcphost/oauth/client.json`, REQ-AUTH-012) as
   `client_id`, fetch it, and accept the portless loopback redirect
   `http://127.0.0.1/callback` with an ephemeral port at authorization time (RFC 8252 §7.3
   port variance)?
2. What does that AS do with the `iss` authorization-response parameter (RFC 9207)?
3. When CIMD is not available, does the fallback chain — Dynamic Client Registration
   (deprecated, compatibility), then a configured `client_id` — obtain a token?

TD §10 exit criterion: "Token obtained via CIMD or documented fallback".

## What was tried

No throwaway spike was written: the prerequisite (access to a real AS advertising CIMD) was
never met, so the question was answered as far as possible by the shipped test suite against
the fixture AS (F4-09a), which resolves the CIMD URL from the repository's
`docs/oauth/client.json` instead of the network.

Verified (all green in CI on `develop`, both eras where marked):

- **CIMD first.** `tests/integration/auth/test_registration.py::test_cimd_as_uses_the_metadata_document_url`
  — an AS advertising CIMD gets the CIMD URL as `client_id`, no `/register` call, stored
  source `cimd` (REQ-AUTH-003).
- **CIMD redirect rules.** `tests/integration/auth/test_fixture_as.py::test_cimd_client_needs_a_loopback_redirect`
  — the CIMD client is accepted only with a loopback redirect; any port only while port
  variance is on; the portless form always; never with CIMD off (REQ-AUTH-012, RFC 8252 §7.3
  as modelled by the fixture).
- **DCR fallback.** `test_registration.py::test_non_cimd_as_falls_back_to_dcr` — without CIMD
  the Host registers as a native app, source `dcr`, and authorizes with the registered
  loopback redirect.
- **Configured `client_id`.** `test_registration.py::test_configured_client_id_skips_cimd_and_dcr`
  (used as is, no CIMD, no DCR) and `test_neither_cimd_nor_dcr_requires_a_client_id`
  (`auth_required` / `client_id_required` with the configuration hint, no authorization
  request).
- **Issuer and resource binding.** `test_registration.py::test_issuer_switch_never_reuses_old_credentials`
  (CIMD, DCR and configured: no old-issuer token or `client_id` reaches the new issuer,
  REQ-AUTH-011), `tests/integration/auth/test_resource_binding.py` (a URL change clears the
  stored entry), `test_fixture_as.py::test_iss_is_emitted_when_enabled` and the mix-up tests.
- **Both eras.** `tests/interop/test_oauth.py` — {modern, legacy} Streamable HTTP ×
  {CIMD, DCR, configured} full flows, mix-up (`iss`), issuer switch and refresh (F4-09b).
- **Document.** `tests/unit/test_cimd_document.py` — the versioned document parses as SDK
  client metadata, its `client_id` is the default `oauth_client_metadata_url`, loopback
  redirects only, no secret-looking keys (REQ-AUTH-012).

Not verified:

- A **real** authorization server fetching `https://blog.seraph.to/reflex-mcphost/oauth/client.json`,
  accepting it as `client_id`, and accepting the ephemeral loopback port against the
  portless registered redirect.
- A real AS's `iss` behaviour and its error text when it rejects the document.

## Answer

1. **Unanswered for real servers.** Against the fixture AS — which implements the CIMD
   draft and RFC 8252 §7.3 as the project reads them — CIMD with the portless loopback
   redirect works end to end on both eras. Whether a real AS accepts it is unknown.
2. `iss` is checked before redemption when the AS sends it and tolerated when it does not
   (fixture toggles); a real AS's behaviour is unknown.
3. **Yes.** The fallback chain CIMD → DCR → configured `client_id` obtains a token against
   the fixture AS on both eras, with issuer and resource binding. This is the "documented
   fallback" branch of the TD §10 exit criterion.

**Decision — plan B (owner, 2026-11-01).** No real CIMD-capable authorization server is
available to the owner. `0.1.0` ships with the tested fallback chain: the CIMD document is
published at `https://blog.seraph.to/reflex-mcphost/oauth/client.json` and offered first
when the AS advertises CIMD, then DCR, then a configured `client_id`. CIMD interop against
a real AS is **unverified** and listed as a known limitation in `CHANGELOG.md` `[0.1.0]`.
S-4 no longer gates F8-07b.

## Residual risk

Plan R-9 (accepted): a real AS may reject the document (portless loopback redirect, port
variance, a fetch or caching rule the fixture does not model), in which case the user sees
the AS's authorization error. Impact is bounded: an AS without CIMD support never receives
the CIMD URL (DCR is used), and any user can configure a `client_id` registered with the AS
(`[servers.<id>.oauth] client_id`, REQ-AUTH-003). The document URL is frozen from `0.1.0` on
(REQ-AUTH-012), so a fix that only changes the document's content (e.g. adding redirect
forms) needs no URL change.

## Impact

- **DD-009 confirmed against the fixture AS**; real-AS acceptance unverified (TD DD-009
  consequences, Plan R-9). No Delta Spec to the PRD, API Spec or Data Model: no requirement,
  interface or schema changes.
- F0-04 closed with plan B; F8-07b no longer depends on F0-04 (delta
  `changes/_archive/2026-11-safari-s4-decisions`).

## Re-opening

When a real authorization server advertising `client_id_metadata_document_supported` becomes
available: run the original F0-04 procedure against it with the live CIMD URL (redirect
`http://127.0.0.1:<ephemeral>/callback`, then force DCR), record the AS, its version, port
variance and `iss` behaviour here, with no token or code value (Art. 5). A pass removes the
known limitation in the next release's CHANGELOG; a rejection opens a Delta Spec (document
content, or a documented per-AS workaround) shipped as a **patch release** (`0.1.x`) —
never a change of the frozen URL.
