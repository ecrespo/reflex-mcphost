# S-6 — Adapter shapes (PydanticAI `AbstractToolset`, LangChain tools)

> Task: F0-06 · REQ-TLS-006/007 (informs), REQ-TLS-004/005 (checked) · Date: 2026-10-31
> Spike code: `spikes/S-6/` (throwaway, not merged) · Timebox 0.5 d — within budget.

## Question

1. Which base class, abstract members and data types does PydanticAI `>=2.64,<3` require for
   a toolset whose tools come from a runtime catalog with raw JSON-schema inputs? How is a
   Host denial returned to the model (vs raised)? Is the toolset re-listed per run, as
   API §4.13 claims?
2. Can `langchain-core>=1.7,<2` build an async tool from a **dict** JSON-schema
   `args_schema`? How should a Host error be surfaced so a LangGraph `ToolNode` returns it
   to the model as a tool error instead of crashing the graph?
3. Does API §4.13 (`as_pydantic_ai_toolset(toolset) -> AbstractToolset`,
   `as_langchain_tools(toolset) -> list[BaseTool]`, dynamic re-listing, denial as tool
   error) hold as written?

## Answer

### PydanticAI 2.64

- Base class `pydantic_ai.toolsets.AbstractToolset[AgentDepsT]` (ABC, also re-exported from
  `pydantic_ai`). `__abstractmethods__ == {"id", "get_tools", "call_tool"}`:
  - `id` — abstract **property** `-> str | None`. `None` is accepted by a normal `Agent`;
    an explicit id is required only for durable execution (Temporal etc.). Ids in angle
    brackets (`<agent>`, `<output>`) are reserved.
  - `async get_tools(self, ctx: RunContext[AgentDepsT]) -> dict[str, ToolsetTool[AgentDepsT]]`
  - `async call_tool(self, name: str, tool_args: dict[str, Any], ctx: RunContext[AgentDepsT], tool: ToolsetTool[AgentDepsT]) -> Any`
  - Optional hooks with defaults: `for_run`, `for_run_step`, `__aenter__/__aexit__`,
    `get_instructions`, `get_tool_for_tool_def`.
- A tool is `ToolsetTool(*, toolset, tool_def: ToolDefinition, max_retries: int, args_validator: SchemaValidator | SchemaValidatorProt, args_validator_func=None)`
  (kw-only dataclass). The raw JSON schema goes into
  `ToolDefinition(name=..., description=..., parameters_json_schema=<dict>, metadata=...)`.
  There is no JSON-schema validator in pydantic-core; PydanticAI's own `MCPToolset` uses a
  permissive `SchemaValidator(dict_schema(str_schema(), any_schema()))` and leaves
  argument validation to the server. The adapter should do the same (the Host validates).
- **Denial**: raise `pydantic_ai.ToolFailed(outcome.text)`. Observed results:

  | Strategy in `call_tool` | What the model receives | Run |
  |---|---|---|
  | return `outcome.text` | `ToolReturnPart(outcome="success")` | continues — error flag lost |
  | raise `ToolFailed(text)` | `ToolReturnPart(content=text, outcome="failed")` | continues, no retry budget consumed |
  | raise `ModelRetry(text)` | retry prompt | aborts with `UnexpectedModelBehavior` after `max_retries` |

  `ToolFailed` is exactly what `MCPToolset(tool_error_behavior="failed")` does for
  `isError` results.
- **Re-listing**: `get_tools` is called by `ToolManager.for_run_step` once **per run step**
  (before every model request), not only per run. Observed: 3 model requests → 3
  `get_tools` calls; a tool added to the catalog after step 1 was visible and callable in
  step 2 of the *same* run (PydanticAI inserted a `ToolAvailabilityDeltaPart` into the
  history); a second run re-listed again. No `DynamicToolset`/`for_run` override is needed.
- Cosmetic: 2.64 prints a startup banner; `PYDANTIC_AI_NO_BANNER=1` silences it (tests/CI).

```python
import pydantic_core
from pydantic_ai import RunContext, ToolFailed
from pydantic_ai.tools import ToolDefinition
from pydantic_ai.toolsets import AbstractToolset, ToolsetTool

_ARGS = pydantic_core.SchemaValidator(pydantic_core.core_schema.dict_schema(
    pydantic_core.core_schema.str_schema(), pydantic_core.core_schema.any_schema()))

class HostToolset(AbstractToolset[Any]):
    def __init__(self, toolset, *, id: str | None = None, max_retries: int = 1):
        self._toolset, self._id, self._max_retries = toolset, id, max_retries

    @property
    def id(self) -> str | None:
        return self._id

    async def get_tools(self, ctx: RunContext[Any]) -> dict[str, ToolsetTool[Any]]:
        return {s.name: ToolsetTool(
                    toolset=self,
                    tool_def=ToolDefinition(name=s.name, description=s.description,
                                            parameters_json_schema=s.input_schema),
                    max_retries=self._max_retries, args_validator=_ARGS)
                for s in self._toolset.list()}

    async def call_tool(self, name, tool_args, ctx, tool):
        outcome = await self._toolset.call(name, tool_args)
        if outcome.is_error:
            raise ToolFailed(outcome.text)
        return outcome.text

# Agent(TestModel(), toolsets=[HostToolset(fake)]).run("go") → both tools called;
# denial arrives as ToolReturnPart(outcome="failed").
```

### LangChain (langchain-core 1.7.3, langgraph 1.2.19)

- **Dict `args_schema` is supported**: `BaseTool.args_schema: type[BaseModel] | dict[str, Any] | None`
  (`ArgsSchema = TypeBaseModel | dict[str, Any]`). With a dict:
  `tool_call_schema` = the dict plus `description`; `convert_to_openai_tool(tool)` emits the
  dict unchanged as `parameters`; `tool.args` = `schema["properties"]`.
  - **No validation**: `_parse_input` returns the dict input as-is (a call missing a
    required arg reached the coroutine). The Host must validate.
  - String input is rejected (`ValueError: String tool inputs are not allowed when using
    tools with JSON schema args_schema`).
- **Async**: `StructuredTool(..., coroutine=async_fn)` works; with no `func`, sync
  `invoke` raises `NotImplementedError("StructuredTool does not support sync invocation.")`.
  Invoking with a `ToolCall` dict (`{"type":"tool_call","id":...,"name":...,"args":...}`)
  returns a `ToolMessage`; a plain args dict returns the raw content.
- **Errors**: raise `langchain_core.tools.ToolException(outcome.text)` **and** set
  `handle_tool_error=True` on the tool → `ToolMessage(content=text, status="error")`.
  Without `handle_tool_error`, the exception propagates and LangGraph's `ToolNode` default
  handler (`_default_handle_tool_errors`) re-raises everything except its own
  `ToolInvocationError` → the graph run fails. So the tool, not the `ToolNode`, must own
  the conversion. Returning plain text would lose `status="error"`.
- **Surprise — reserved kwarg collisions in `StructuredTool`**: arguments are passed to
  `StructuredTool._arun(*args, config, run_manager, **kwargs)` as kwargs. For a JSON-schema
  property named `run_manager` or `config` the model's value is **silently replaced/dropped**;
  a property named `self` raises `TypeError: _arun() got multiple values for argument 'self'`
  (`callbacks` survived). MCP tools may legitimately have a `config` argument.
  Fix verified: subclass `BaseTool` directly, override `_to_args_and_kwargs` to pass the
  argument dict positionally, and give `_arun` no `config`/`run_manager` parameters (so
  LangChain injects nothing). All of `callbacks`, `run_manager`, `config`, `self`, `q`
  arrived intact; `ToolNode` returned `'3' success` and the denial with `status='error'`.
  Caveat: `_to_args_and_kwargs` is a private method — pin it in the contract test.
- **`ToolNode`** (`langgraph.prebuilt`, from `langgraph-prebuilt` 1.1.1) must run inside a
  graph in langgraph 1.2 (standalone `ToolNode.ainvoke` → `ValueError: Missing required
  config key 'N/A' for 'tools'`). One agent step through `StateGraph(MessagesState)` with
  `model → tools_condition → ToolNode → model` produced
  `ToolMessage('Permission denied by the host: …', status='error')` and a final AI answer.
  `langgraph.prebuilt.create_react_agent` still works but warns that it has moved to
  `langchain.agents` (the separate `langchain` package) — examples should build the graph
  or depend on `langchain` explicitly.

```python
from typing import Any
from langchain_core.tools import BaseTool, ToolException

class HostTool(BaseTool):
    toolset: Any
    handle_tool_error: Any = True

    def _to_args_and_kwargs(self, tool_input, tool_call_id):   # pass the dict as one positional arg
        return (dict(self._parse_input(tool_input, tool_call_id)),), {}

    def _run(self, arguments: dict[str, Any]) -> str:
        raise NotImplementedError("async only")

    async def _arun(self, arguments: dict[str, Any]) -> str:
        outcome = await self.toolset.call(self.name, arguments)
        if outcome.is_error:
            raise ToolException(outcome.text)
        return outcome.text

def as_langchain_tools(toolset) -> list[BaseTool]:
    return [HostTool(name=s.name, description=s.description, args_schema=s.input_schema,
                     toolset=toolset, metadata={"fqn": str(s.fqn)}) for s in toolset.list()]
```

(The simpler `StructuredTool(name=..., description=..., args_schema=<dict>, coroutine=_call,
handle_tool_error=True)` variant is in `spikes/S-6/lc_spike.py` and works except for the
collisions above.)

## Impact

- **API §4.13 holds as written** — no API Delta Spec required:
  - `as_pydantic_ai_toolset(toolset) -> AbstractToolset` ✔ (return a subclass instance).
  - `as_langchain_tools(toolset) -> list[BaseTool]` ✔ (elements are a `BaseTool` subclass).
  - "PydanticAI toolsets are re-listed per run" ✔ — actually stronger: re-listed per run
    *step*, so REQ-TLS-004 is met mid-run as well. "LangChain tools are a snapshot" ✔ (each
    tool is a static object; callers rebuild after `catalog.changed`).
  - Denial as tool error (REQ-TLS-005) ✔ in both: `ToolFailed` → `outcome="failed"`;
    `ToolException` + `handle_tool_error=True` → `status="error"`. `Toolset.call()` must
    keep its "never raises for outcomes" contract, because LangGraph's `ToolNode` will
    crash the graph on any other exception (e.g. a stray `KeyError`).
  - Optional wording improvement (editorial, not normative): "re-listed per run step".
- **Delta Spec required (Technical Design, small)**: `specs/technical/mcphost-architecture.md`
  component table row "Adapters" names LangChain `StructuredTool`; because of the silent
  kwarg-collision bug the adapter should be a direct `BaseTool` subclass. Also §0 / extras
  should name the distributions: extra `pydantic-ai` → `pydantic-ai-slim>=2.64,<3` (no
  provider SDKs pulled), extra `langgraph` → `langchain-core>=1.7,<2` (+ `langgraph>=1.2,<2`
  only for examples/`ToolNode`; the adapter module itself imports only `langchain_core`).
  Proposed change id: `changes/<date>-adapter-shapes/` (to be opened at review; not created
  by this spike).
- Implementation notes for F5-03/F5-04: no JSON-schema validation happens in either framework
  — the Host's `Invoker` must validate `arguments` against `input_schema` and turn failures
  into an error outcome. Set `PYDANTIC_AI_NO_BANNER=1` in the test environment.
